# 分支与协作规范

> 适用对象：本仓库全部成员。新人请先读本文，再动手改代码。
> 本文写于 2026 年仓库整理之后，反映**整理后**的实际状态。

---

## 1. 一句话规则

> **`main` 是唯一集成分支。任何人不要直接往 `main` 推代码；
> 一律"开分支 → 改 → 提 PR → 合并"。**

## 2. 分支模型

```
main          ●────●──────────────●──────────►   永远可运行，只放集成好的成果
               \       \         /
feature 分支    ●───●   ●───●   ●             各自开发，完成后提 PR
```

### 2.1 长期分支

| 分支 | 用途 | 谁能推 |
| --- | --- | --- |
| `main` | 集成分支，最新可运行版本 | **只接受 PR 合并**，不直接推 |

### 2.2 工作分支命名

| 前缀 | 用途 | 例子 |
| --- | --- | --- |
| `feat/` | 新功能 | `feat/ann-accept-head` |
| `fix/` | 修 bug | `fix/ann-manifest-path` |
| `data/` | 数据相关改动 | `data/add-carla-data8.6` |
| `docs/` | 只改文档 | `docs/snn-readme` |
| `exp/` | 实验性代码，允许不完整 | `exp/snn-margin-calibration` |
| `chore/` | 工程杂项（依赖、配置） | `chore/upgrade-torch` |

建议前缀后面带上**模块名**，一眼看出是谁的活：`feat/snn-...`、`feat/ann-...`、`data/carla-...`。

### 2.3 历史遗留分支

整理时保留下来的旧分支（`master`、`ANN`、`Carla`、`satan`、
`Robot_Collision_Avoidance_Data`）内容**都已经在 `main` 里了**。
新工作**不要再基于它们开分支**，从 `main` 开。

## 3. 日常流程（照抄即可）

### 3.1 第一次：克隆并切到 main

```bash
git clone https://github.com/xX-uYang/SNNObstacleAvoidance.git
cd SNNObstacleAvoidance
git switch main
```

> ⚠️ **Windows 用户注意**：不要改 `core.autocrlf`。
> 仓库用 `.gitattributes` 统一了换行符，改了会看到"整个仓库都被修改"的假 diff。

### 3.2 每次开工前

```bash
git switch main
git pull                      # 先同步别人的改动
git switch -c feat/ann-我的功能
```

### 3.3 干活、提交

```bash
git status                    # 看清自己改了什么
git add 具体文件               # 别用 git add -A，容易把缓存/权重/数据带进去
git commit -m "feat(ann): 增加 accept 判定头"
git push -u origin feat/ann-我的功能
```

**提交信息格式**（约定式提交，中英文都行）：

```
<类型>(<范围>): <摘要>

可选的详细说明：为什么改、改了什么、怎么验证的
```

- 类型：`feat` `fix` `docs` `refactor` `test` `chore` `data` `exp`
- 范围：`ann` `snn` `carla` `router` `data` `repo` 等
- 摘要用**动词开头**，说清"做了什么"，不要写 "update"、"修改一下"。

✅ 好例子：
```
fix(ann): 修正清单里 500 条失效的图片路径

图片移到 Collision_Avoidance_System_Data/ 子目录后，
manifest 的 image_path 仍是旧路径，导致 load_manifest 抛 FileNotFoundError。
只改 image_path 列，train/val/test 划分保持不变。
验证：load_manifest 成功加载 625 行，447/90/88。
```

❌ 坏例子：`更新`、`改了一下`、`fix bug`、`123`

### 3.4 提交前自查（30 秒，别跳）

```bash
git status                     # 有没有 __pycache__ / *.pt / 数据集混进来？
python -m unittest discover -s tests -v     # ANN 侧：12 项测试应全过
git diff --cached --stat       # 改动规模符不符合预期？
```

### 3.5 提 PR

1. 推到自己的 `feat/...` 分支后，在 GitHub 上点 **Compare & pull request**。
2. 标题同提交信息格式，例如 `feat(ann): 增加 accept 判定头`。
3. 描述里写清三件事：**改了什么 / 为什么 / 怎么验证的**。
4. 目标分支选 `main`。
5. 至少找 **1 个了解该模块的人** review（ANN 相关找 `@jk-Huo`，
   SNN 相关找 `@xX-uYang`，数据相关找 `yzy`）。
6. 合并方式：**Squash and merge**（把零碎提交压成一条，历史干净）。

### 3.6 合并后

```bash
git switch main
git pull
git branch -d feat/ann-我的功能     # 本地删掉已合并分支
```

## 4. 多人协作中最容易踩的坑

### 4.1 冲突了怎么办

**不要慌，也不要强推。** 冲突只是"两个人改了同一行"：

```bash
git switch main && git pull       # 先把 main 最新拉下来
git switch feat/我的功能
git merge main                    # 把 main 合进自己的分支，冲突在自己分支里解
# 打开冲突文件，找 <<<<<<< ======= >>>>>>> 三处标记，
# 手动改成你想要的样子，然后删掉这些标记
git add 冲突文件
git commit
git push
```

冲突解决完**必须跑测试**再推。

### 4.2 千万别做的事

| ❌ 不要 | 原因 |
| --- | --- |
| `git push --force` 到 `main` | 会覆盖别人的提交，且历史找不回来 |
| `git push -f` 到**别人正在用的**分支 | 同上；自己独占的 `feat/` 分支可以 |
| `git add -A` / `git add .` | 极易把 `__pycache__`、`*.pt`、几百 MB 数据集一起提交 |
| 提交 `.env`、token、密钥 | 见第 6 节 |
| 修改 `core.autocrlf` | 会污染整仓库 diff |
| 直接在 GitHub 网页上改别人分支的文件 | 冲突难收拾，走 PR |

### 4.3 我自己分支搞乱了，想重来

```bash
git fetch origin
git switch main
git pull
git branch -D feat/我的功能            # 丢掉搞乱的分支
git switch -c feat/我的功能-2          # 重新开一个
```

已经写好的代码如果在别的目录，直接复制过去即可。

## 5. 数据与产物怎么传

**图片、数据集、模型权重一律不进 Git。** 原因：仓库要长期保持小体积，
Git 存大文件后即使删掉，历史里仍然占空间。

传递方式：
- 数据：网盘 / 移动硬盘，交接后放到本地 `carla_data/`（仓库根目录，已被忽略）。
- 权重：同上；如果必须进仓库，另开分支并配 Git LFS（**需先和大家讨论**）。
- 实验结果：只把小体积的 `metrics.json` / `predictions.csv` / 说明 `.md` 提交到 `runs/`。

## 6. 安全红线 🔒

- **绝不提交**任何形式的凭据：GitHub / OpenAI / AWS / Slack token、私钥、密码、
  API key、`.env` 文件、`service-account.json`、`kaggle.json`。
- 代码里需要用到 token 时，**只从环境变量读**：
  Python 用 `os.environ["GITHUB_TOKEN"]`，Node 用 `process.env.GITHUB_TOKEN`，
  并且**不要打印出来**、不要写进日志、不要写进命令行（命令行会进 shell 历史）。
- 一旦不小心提交了 token：
  1. **立刻去平台吊销/重置该 token**（最重要，比清理历史还重要）；
  2. 再想办法清理历史（`git filter-repo` 等），并通知所有人重新 clone；
  3. 只删文件不删历史 = 没删，别人 `git log` 还能翻出来。
- 本仓库是 **Public**：不要提交内部资料、客户名、本机绝对路径、
  个人邮箱/手机号等不希望对外的信息。
